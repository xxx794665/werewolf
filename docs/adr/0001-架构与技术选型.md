# ADR 0001：架构与技术选型

日期：2026-10-02 ｜ 状态：已接受 ｜ 决策人：功能规划（ponytail 口径）

## 决策

**无构建静态站 + Cloudflare Workers + Durable Objects + HTTP 轮询。** 前端原生 HTML/CSS/JS 直接推 GitHub Pages，不经过 CI；后端一个房间 = 一个 DO 实例（SQLite 后端），DO 是游戏状态机与唯一权威。第一版不用 WebSocket：母本同款 HTTP 短轮询（1.5s、`rev` 游标、`unchanged` 短回包）已验证够用，跑通再升。理由：零构建 = 无依赖无 CI 无构建产物；DO 免费额度内且天然单房间串行，免锁。

**单机即私密房间。** 单机模式不另写一套游戏逻辑，就是一个 1 真人 + 8 AI 的普通房间（房号不对外展示）。一套状态机、一套测试。砍掉「单机本地引擎」的理由：第二套内核 = 第二倍 bug 面，YAGNI。

**游戏内核单份共享模块。** 板子定义、胜负判定、阶段推进放 `shared/game.js` 纯函数，DO（权威执行）与前端（渲染）共同 ESM import。快照按请求者座位裁剪私有字段，从结构上保证「AI 与玩家只见该见的」。理由：判定逻辑写两份必然漂移；裁剪放服务端是安全边界，不简化。

**AI 由客户端驱动（单机 = 玩家、联机 = 房主），BYO Key 全存浏览器。** Worker 只做 `/api/ai-proxy` 透传（解 CORS），Key 不落服务端。代价：房主掉线 AI 暂停、AI 提交可被伪造——联机本就互信，接受并写入非目标；换来的是零服务端 Key 管理。

**BYO 仅支持 OpenAI 兼容 `chat/completions` 一种格式。** 覆盖绝大多数上游与中转（含 Anthropic 兼容网关）；Anthropic / Gemini 原生格式延后。房间人数固定 9（3 狼 3 民 预女猎），不可设置：一套平衡板子、一套提示词、一套流程测试；可变板子延后。

**对需求的两处刻意收窄**（已在 features.md §13 立账）：「房间设置人数」收窄为固定 9；「补足 AI」统一为「有空位一律提示补到 9」。

**安全不简化：** url-guard（母本 `worker/src/url-guard.js` 照抄）应用于一切服务端出站 fetch，配 `node --test` 用例。测试命令用 `node --test`（自动发现）；本机实测 `node --test test/` 在 cmd 下报 MODULE_NOT_FOUND，不用该写法。

## 后果

- 轮询有最多 ~1.5s 延迟：狼人杀回合制，可接受。
- 房主是联机 AI 的单点：接受（非目标 #9）。
- 狼队长独裁定刀、屠城判定、暗牌、固定发言顺序：均为砍分支的最简口径，见 features.md §5。
