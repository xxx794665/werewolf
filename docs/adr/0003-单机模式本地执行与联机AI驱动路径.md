# ADR 0003：单机模式本地执行；联机 AI 驱动走 drive_ai

日期：2026-10-03 ｜ 状态：已实施；features.md / docs/ai-prompts.md 口径已于 2026-10-03 随验收修复同步修订 ｜ 背景：前端落地时发现两个「冻结口径与已实现内核/快照形状相冲突」的阻断点。

## 决策

**单机模式在浏览器本地执行，不建 Worker 房间。** features.md §2/§6 写「单机 = 一个私密房间，复用联机全部代码」，但内核 `start` 要求真人 ≥ 3（§7.4 最小开桌数，DO 是唯一入口），1 真人局在 Worker 侧原子开不了桌（后端已在 test/worker.test.mjs 白盒注明该 gap）。拍板：单机 = 玩家浏览器本地跑 **同一份** `shared/game.js` 内核（join → ready → `start(solo:true)`，`solo` 开关仅本地使用、DO 路由 `room-logic.js` 的 start 不下发该字段，联机行为不变）；AI 发言 / 夜行动按 docs/ai-prompts.md §5.2 客户端路径：`roleCardOf` + `windowHistory` + `buildMessages` → `/api/ai-proxy` → §5.1 解析 → 失败走 `applyFallback`。单机状态存 localStorage（`ww_solo`），刷新可恢复；不设行动超时（§5.11 本就豁免单机）。「不存在第二套游戏逻辑」的规则口径保持成立（同一份内核），放弃的是「单机复用联机房间通道」这一实现路径。拒绝的替代方案：本地伪造 3 个真人 uid 开局再改标（脏数据进内核，测试已在用的白盒手法不能上生产路径）。

**联机 AI 驱动走 `act(drive_ai)`（服务端发起，ai-prompts.md §5.3.2 路径）。** 冻结口径 §5.3.1 是房主客户端经 `ai_view` 驱动，但夜里快照对一切非行动座位冻结（§4.1.6 / ADR-0002），房主客户端拿不到「夜里轮到哪个 AI 座位、是什么任务」，纯客户端路径在夜里无法驱动；白天虽可行，双路径并存徒增两套驱动代码。拍板：联机统一走后端已实现的 `drive_ai`（房主带 BYO baseUrl/model/key 调用，Key 瞬态透传不落盘，DO 组装提示词 + url-guard + 回退兜底）；房主侧触发 = 快照变化 + 4s 兜底节拍（夜里房主快照也冻结，不能只靠快照）。Key 来源即 §5.3.2 的选项 a 变体（按请求瞬态携带，比「开局存 DO 内存」更轻）。若日后要回到纯客户端路径，需 DO 对 owner 快照额外暴露「待驱动座位 + 任务类型」（夜里），另行记 ADR。

## 后果

- 单机离线可玩性更好（除 AI 请求外无网络依赖）；代价是单机不经过 DO，§7.7 的托管/超时体系与单机无关（本就豁免）。
- `shared/game.js` 多一个 `solo` 动作字段；联机校验路径不变（game-core 24/24 回归通过）。
- 联机 AI 驱动的 Key 按请求透传给 DO 内存瞬态使用——「服务端不落盘」成立，「Key 不出客户端」放宽为「不出本次请求」，与 §5.3.2 选项 a 同级。
- features.md §2「单机 = 一个私密房间」「AI 决策一律由客户端发起」两处措辞与现状不符，需 owner 拍板后修订（本 ADR 即修订依据）——已于 2026-10-03 随验收修复完成修订（features.md §2 / §6 / §7.6 / §8.1 / §9 / §13.9 与 docs/ai-prompts.md 同步，见 docs/TASKS.md 同日条目）。
